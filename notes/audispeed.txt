================================================================
  ANALYSE — save_snapshot : nécessaire ou optionnel ?
================================================================

save_snapshot est purement analytique — aucun rôle dans le trading.

Rôles distincts :
  - Trades (entrée, résolution, PnL) → check_signal + check_resolution
    opèrent sur l'état EN MÉMOIRE (TokenState, BotState). Pas de DB.
  - Table snapshots → uniquement pour reconstituer les données post-session
    et alimenter le backtest (c'est ainsi qu'ont été créés basicsunday.db,
    calmsaturday.db, etc.)
  - Le garde ask_vol > 0 dans check_signal (live_bot.py:419) vérifie
    l'état en mémoire, pas la base de données.

Coût réel en production (50 tokens actifs) :
  50 tokens × 1 snapshot/5s = 10 INSERT/s = 10 fsyncs SQLite/s en continu
  Chaque INSERT coûte ~19 µs dont ~9 µs execute + ~9 µs commit (fsync).
  Non critique mais I/O inutile si la collecte de données n'est pas souhaitée.

Solution proposée — constante optionnelle :

  ENABLE_SNAPSHOTS = True  # False pour réduire les écritures SQLite

  Dans handle_book_update :
    if ENABLE_SNAPSHOTS and now - ts.last_snapshot_ts >= SNAPSHOT_INTERVAL:
        save_snapshot(state, ts)
        ts.last_snapshot_ts = now

  Alternative : argument CLI --no-snapshots au lancement,
  sans modification du code source.
